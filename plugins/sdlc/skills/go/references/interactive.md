# Interactive

The request comes from the user, in this session, and the user can answer. SKILL.md's rules hold; this is the sequence.

0. **Preflight.** `sdlc.py status --json`. Exit 2 ("no .sdlc/config.json") or `legacy_config: true` → say in one line that `/sdlc:init` has to run first (adopting a repository is the user's decision — do not run it for them) and stop. `loop.running: true` → a loop owns this checkout; tell the user to `sdlc.py stop` it or work in another worktree, and stop. `git status --porcelain` not empty → ask the user to commit or stash first, and stop. Read `.sdlc/config.json`: `language`, `mode`, `paths.work`, `commands`, `verify`.
1. **Work doc.** From the request and what the repository itself answers, write `work/<slug>.md` from `${CLAUDE_PLUGIN_ROOT}/templates/<language>/work.md` (format: references/work-doc.md): a kebab-case ascii slug of at most five words that is not yet a doc, a branch or a remote branch, and not `readme` or `template`; title; Goal; Acceptance criteria `R1. WHEN … THE SYSTEM SHALL …`; `status: ready`; `source: user`; `created` from `date -u +%Y-%m-%dT%H:%M:%SZ`, never typed from memory. Ask at most two questions, and only when scope or success is genuinely ambiguous — numbered, each with a recommended answer. Several independent changes in one request → say so and offer `/sdlc:run`.
2. **Branch.** With a remote, `git fetch -q origin`. `git switch -c sdlc/<slug> <base>` (the untracked doc comes along), then `mkdir -p .sdlc/state && printf '%s\n' <slug> > .sdlc/state/active-work`. The hooks read that file (test lock, design-first) and ignore it when the branch does not match it.
3. **Design** (references/design.md). Team mode: step 8 there is the user's approval of the plan; solo goes on without asking.
4. **Build.** Task → `sdlc:sdlc-builder` (model sonnet) with the doc path — also for a change that looks small: the build's output stays out of this session. It implements, tests and commits `sdlc(<slug>): build`, and leaves the status `planned`. Read its report: open issues that need the user → ask; departures → check them against the Plan. Then add the checks of references/build.md (verifier, simplifier). If the agent cannot run, build in this session by references/build.md.
5. **Review** (references/review.md): the reviewer pass through Task, each Important finding validated in a fresh context, confirmed ones fixed (small → you; larger → back to the builder with the finding), tally recorded in `## Review`, `status: built`, commit `sdlc(<slug>): review`.
6. **Ship.** Run `sdlc.py ship <slug>` in the background (`run_in_background: true`) and wait for its completion notification — do not poll. It is the same shell gate and merge the loop uses (tree clean, doc `built`): it reruns the gate commands and, on GitHub, then waits for the PR's checks, up to `loop.checks_wait_minutes` (30 by default). Read its output when the notification comes. Exit 0: merged (by the engine, or by a person during the wait), or in team mode handed to a person — print the PR. Exit 1: the output is the fix brief — the gate's, or the PR's failed checks (the doc went back to `built`) — fix it per references/fix.md, commit, ship again; at most three rounds, then stop and report with the literal output. Exit 2: a person has to decide — report the reasons and where the change lives (`gh pr list --head sdlc/<slug> --json url,state`, or the branch when there is no PR); do not work around them and do not merge it yourself. Untracked build output that blocks `ship`: delete it or add it to `.gitignore` (note it in Departures); never commit it.
7. **Wrap up** (also when you stop early). `rm -f .sdlc/state/active-work`. A shipped or handed-over change: return to `<default>` and update it (`git switch <default>`; with a remote `git pull --ff-only`; when `<default>` is checked out in another worktree, `git switch --detach <base>`). An unfinished one stays on its branch — say so. Report in the user's language: what changed (behavior, not a file list), the proof results (literal tail), the review tally and any `proposed` docs it wrote, the PR link / "merged locally" / "waits for you to merge", and what is left for the user.

**Resuming.** The user names a change already under way, or `git branch --list 'sdlc/*'` shows the obvious one: `git switch sdlc/<slug>`, write `active-work` again, read its doc and continue at the step its status shows — `ready` → 3, `planned` → 4, `built` or `done` → 6. Do not redo committed work.
