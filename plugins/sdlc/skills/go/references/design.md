# Design

Turn a `ready` doc into a plan that someone who never saw this conversation could build from. Interactive: you do it in the main session. Loop (`--item <slug> --design`): you are on `sdlc/<slug>` and the doc says `ready`.

1. **Read.** The doc (Goal, Acceptance criteria, and `## Questions` with its `**Answer**` lines if there are any), CLAUDE.md (Architecture, Conventions, Things Claude gets wrong), `.sdlc/config.json` (`commands`, `risk.human`, `gate`). For anything wider than a couple of files — where does X live, how does this flow work, which tests cover it — ask `sdlc:sdlc-researcher` (Task, read-only, haiku) and use its answer, not its file dumps.
2. **Settle the criteria.** They are yours to sharpen until the doc is `planned`: make each one testable (`R1. WHEN … THE SYSTEM SHALL …`, one behavior, observable, the edge or error case that matters) and add what is missing. Never drop or weaken one a person wrote. Contradicting criteria, or one that cannot be tested as written, is a question, not a guess (references/questions.md). After `planned` they are frozen.
3. **Write the Plan** in the doc:
   - numbered steps, each independently checkable and each with how it is checked — `2. Add POST /entries with validation — tests/test_entries.py`;
   - **Files** — every file that changes, `(new)` or `(modified)`;
   - **Risks** — answer three questions: what could this break, which step is the riskiest, which other approaches were considered and why they were not chosen.

   More than about eight steps or fifteen files is probably more than one PR. Interactive: say so and offer `/sdlc:run` to split it. Loop: order the steps so each one leaves the build green, and say in Risks what makes it big.
4. **Write the Proof**: the table `| R | test or command | kind |`, a row per criterion, each naming a concrete test (file and case) or command, kind `unit`, `e2e` or `manual`. Prefer what the build can run. `manual` only when nothing runnable can show it — then say how a person checks. No test command configured: the Proof names the command that shows the behavior, and the report says the gate had nothing to run.
5. **Decide `test_changes`.** `none` (default): the build adds new test files and edits no existing one — the gate sends any edit, rename or deletion of an existing test file to a person. `allowed`: only when existing tests must change — new behavior replaces old behavior, fixtures move — and the Proof says which tests and why, in a line that starts `test_changes:` (it goes into the PR and the merge commit). A bug fix stays `none`: its reproducing test is a new test file. Like the criteria, the value is frozen once the doc is `planned`: the gate sends a later change to a person.
6. **Foresee what the gate will do.** A new dependency: avoid it, or the Plan says why (the gate sends that PR to a person). A file that matches `risk.human` globs: say so in the Plan (a person reviews that PR anyway). The guard files — `.sdlc/config.json`, the frozen-paths file, `.claude/settings.json`, `.claude/settings.local.json`, `checks/` — always go to a person: if the item needs one, the Plan says so. A frozen path (`.sdlc/frozen-paths.txt`, `protect.generated_paths`) cannot be edited at all — plan around it or ask.
7. **Commit.** First `grep -n '^## ' work/<slug>.md`: `## Plan` and `## Proof` must be there with text under them (a doc from `/sdlc:run` has neither at first, so add the sections after Acceptance criteria — references/work-doc.md). Then set `status: planned`, `git add work/<slug>.md`, commit `sdlc(<slug>): design`. Loop: print `SDLC_PLANNED <slug>`. Interactive in team mode: before you set `planned`, show the user the Plan, the Proof and `test_changes` and go on only with their OK — it is their approval of the design; changes they ask for go into the doc first. Solo: go on without asking.

Done when: Plan and Proof are filled, every R has a Proof row, `test_changes` is set, the status is `planned`, the commit exists.

## Instead of a plan

- **A decision only a person can make** blocks the design → `needs-input` and `## Questions` (references/questions.md). Interactive: ask the user and carry on with their answer.
- **Already there, or no longer needed** — and you can point to the file and line or the commit that proves it → `dropped`, with the reason as the first line of `## Departures` (loop: the engine records the drop on `<default>` and closes the item's PR — references/questions.md). Interactive: tell the user and stop; offer to remove the branch and the untracked doc.
- **Back after an answer**: the doc already has a Plan and an `**Answer**` under Questions → revise the Plan and Proof in light of the answer instead of starting over. If the answer changes a criterion, edit just that criterion and quote the answer in `## Departures`.
