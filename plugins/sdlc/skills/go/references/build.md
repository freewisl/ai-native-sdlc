# Build

You are on `sdlc/<slug>` and the doc says `planned`. Interactive: `sdlc:sdlc-builder` did steps 1–4 and 6, you do 5 and 7. Loop (`--item <slug> --build`): this session already runs on the build model (`loop.models.build`) and does all of it itself — no `sdlc-builder` — but the review in step 7 still goes to `sdlc:sdlc-reviewer` through Task.

1. **Read.** The whole doc (Goal, Acceptance criteria, Plan, Proof, `test_changes`, `## Questions` with its answers), CLAUDE.md (Commands, Conventions, Architecture, Things Claude gets wrong), the files the Plan names with their neighbors and tests. First `git status`, `git log <base>..HEAD` and `git diff` — always, not only with `--continue`: a stopped session or an answered question leaves earlier work on this branch. Keep what is right; do not redo committed steps. A `planned` doc whose Plan or Proof is empty never got its design: write them yourself from the criteria first (references/design.md steps 3–4, commit `sdlc(<slug>): design`), say so in `## Departures`, and leave the criteria as they are.
2. **Implement in Plan order**: the smallest change that meets the criteria, in the style of the surrounding code. No features, refactors, renames or dependencies the Plan does not name. After each step run the check the Plan gives for it and commit when it is green (`sdlc(<slug>): build — step 3`).
3. **Tests.** Write the tests the Proof names. New test files are always fine; edit an existing test file only when `test_changes: allowed`. Never weaken, skip or delete a test and never add skip/only/xfail — a failing test means the code is wrong. If an existing test has to change and the doc says `none`, stop and ask (references/questions.md); do not flip the field yourself.
   *Bug fix:* write the test that reproduces it first (a new test file), run it and check it fails for the expected reason — an assertion about the bug, not an import error — commit it, then change the code only.
4. **Verify the way the gate will.** Run what the gate runs: the commands in `gate.commands` (default `build`, `test`, `lint`; each is `commands.<name>` in `.sdlc/config.json`, else CLAUDE.md "Verifying your work"; an empty one is skipped — say so) and every executable in `checks/` (`paths.checks`). Read the real output: the evidence is the toolchain's, not your reading of the code. Fix the code and rerun. After three rounds on one failure step back and re-read the Plan and the assertion: a wrong criterion or a locked test is a question, not something to code around. Long commands: SKILL.md.
   A UI change with a mock: start the app, screenshot it with the project's screenshot script (a loop session has no browser tool), compare with the mock, adjust — two or three rounds — and put the last screenshot path in the Proof results. That screenshot is the UI check. No such script: the UI row stays `manual`, and the Results say so.
5. **Independent checks** — the main session in an interactive run, the loop session itself otherwise (both are top level, so both can launch these agents through Task). Interactive: run the gate's commands once yourself after the builder — its report is not evidence.
   - `sdlc:sdlc-verifier` (fresh context, runs the app or tests, reports only) for behavior the tests do not reach. `verify.agent` decides: `auto` (default) → when the change touches at least `verify.agent_min_files` (4) non-test files, or has behavior the test command does not exercise (a running app, a CLI); `always`; `never`. Give it the commands, the doc path and the changed files. Its verdict does not override your own output, but a mismatch it finds is fixed or written to Departures.
   - `sdlc:sdlc-simplifier` (behavior-preserving cleanup of the changed files, reruns the tests): when the diff is large (roughly 150 changed lines or more) or the build left duplicated or dead code. Skip it for small changes. Rerun the gate's commands only when code changed since the last green run (the simplifier's own run counts); the gate reruns everything before the merge.
6. **Record in the doc** (add a section that is missing — references/work-doc.md): under `## Proof`, after the table, `Results:` lines (`- npm test → exit 0, "Tests: 42 passed"`); one line in `## Departures` for each departure from the Plan with the reason, in the same commit as the code; up to three lines in `## Learned`. Never edit Goal, Acceptance criteria or Plan.
   A change that resolves another open work doc: set that doc to `dropped`, its first `## Departures` line `resolved by <slug> <sha>` (the commit that does it), and commit that too. Interactive: the builder names it under Open issues.
7. **Review** (references/review.md), always through the reviewer agent; it ends with the tally in `## Review`, `status: built` and a commit. Loop: print `SDLC_BUILT <slug>`.

Done when: the gate's commands are green, every R has a result in the Proof, the review tally says `important=0` (or is honest about what is open), the status is `built`, everything is committed and the tree is clean.

## Instead of finishing

- A decision only a person can make (an existing test must change, a criterion turns out wrong, a frozen path or a guard file is needed) → `needs-input` (references/questions.md). Commit the work so far first; it stays on the branch. A new dependency or a `risk.human` path the Plan did not name is not a question: say why in `## Departures`; the gate hands the PR to a person.
- The item is unnecessary — the behavior is already there, with proof → `dropped`, the reason as the first line of `## Departures` (references/questions.md: the engine records the drop on `<default>` and closes the item's PR).
